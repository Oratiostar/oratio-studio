Ce chapitre explique ce qui se passe entre le branchement de l’alimentation et le bureau prêt à l’emploi. Qui a compris cela comprend aussi pourquoi des réglages disparaissent parfois après un redémarrage – par exemple la résolution de l’écran (chapitre 10).

8.1 L’idée de base : la course de relais

Le démarrage est une course de relais. Chaque étape est un programme différent qui n’a qu’une seule tâche : trouver et lancer l’étape suivante. Chaque étape lit ses propres réglages.

Étape Qui court Que lit-elle Tâche
1 Boot-ROM dans la puce rien (intégré en dur) trouve le chargeur d’amorçage
2 Chargeur d’amorçage EEPROM (petite mémoire sur la carte) sa propre configuration dans l’EEPROM (BOOT_ORDER) cherche un support amorçable
3 Firmware config.txt, fichier Device-Tree (.dtb), overlays configure le matériel, charge le noyau
4 Noyau Linux cmdline.txt démarre les pilotes, monte le système de fichiers racine
5 systemd (le premier programme du système) fichiers de service, fstab démarre les services, la connexion
6 Gestionnaire de connexion et session de bureau réglage de la connexion automatique, fichiers de session démarre le gestionnaire de fenêtres (labwc)
7 Gestionnaire de fenêtres (labwc) ~/.config/labwc/…, démarrage automatique dessine le bureau, règle le mode d’écran
8 Programmes personnels entrées de démarrage automatique p. ex. Kanshi, Control Center

8.2 Étapes 1 et 2 : Boot-ROM et EEPROM

Le processeur contient un minuscule programme non modifiable (Boot-ROM). Il lance le chargeur d’amorçage, qui se trouve dans l’EEPROM (une petite mémoire flash) sur la carte. Le chargeur décide d’où démarrer.

sudo rpi-eeprom-config
sudo rpi-eeprom-config | grep BOOT_ORDER
vcgencmd bootloader_version

La valeur BOOT_ORDER est un nombre en hexadécimal, par exemple 0xf461. On la lit de droite à gauche, un chiffre par tentative :

Chiffre Signification
1 carte SD
6 NVMe
4 stockage de masse USB
f recommencer depuis le début

0xf461 signifie donc : d’abord SD (1), puis NVMe (6), puis USB (4), puis de nouveau depuis le début (f). Qui veut démarrer depuis le NVMe mais a une carte SD insérée démarre depuis la carte SD, car elle est essayée en premier. Pour changer : sudo raspi-config → Advanced Options → Boot Order.

Erreur typique : le Pi démarre depuis le mauvais disque. Vérifier avec lsblk (chapitre 7) si le disque attendu est bien reconnu, et avec BOOT_ORDER qui est interrogé en premier.

8.3 Étape 3 : firmware et `config.txt`

Quand le chargeur a trouvé un support, il y lit la partition de démarrage. C’est une petite partition FAT, située sur le Raspberry Pi OS actuel sous /boot/firmware/ (autrefois /boot/).

Fichier Contenu
config.txt Réglages pour le firmware : pilotes (dtoverlay=…), interfaces (dtparam=i2c_arm=on), graphique, surcadençage
cmdline.txt Paramètres pour le noyau, exactement une ligne
*.dtb Device-Tree : décrit le matériel de la carte
overlays/ descriptions matérielles supplémentaires (p. ex. pour les appareils I²C)
kernel*.img, initramfs* le noyau et son système de fichiers de démarrage 
sudo nano /boot/firmware/config.txt
vcgencmd get_config int         # was die Firmware wirklich übernommen hat

Une modification de config.txt ne prend effet qu’après un redémarrage, car le fichier n’est lu qu’à cette étape.

8.4 Étape 4 : le noyau et `cmdline.txt`

Le noyau reçoit du firmware les paramètres de cmdline.txt. On y trouve par exemple quelle partition est le système de fichiers racine :

console=serial0,115200 console=tty1 root=PARTUUID=xxxxxxxx-02 rootfstype=ext4 fsck.repair=yes rootwait

Le noyau démarre ses pilotes, détecte les disques et l’écran et monte le système de fichiers racine. Vérifier ce qu’il a reçu et ce qu’il signale :

cat /proc/cmdline               # Parameter, die der Kernel wirklich bekam
dmesg | head -50                # Meldungen der ersten Sekunden
dmesg | grep -i -E "error|fail|drm|hdmi"

Règle pour cmdline.txt : tout sur une seule ligne, séparé par des espaces. Un saut de ligne ou une faute de frappe peut empêcher le démarrage. Avant toute modification, faire une copie (sudo cp cmdline.txt cmdline.txt.bak).

Pourquoi le PARTUUID est important : il figure dans cmdline.txt et dans /etc/fstab. Qui copie un système sur un autre disque doit adapter les deux (c’est pourquoi l’appli de sauvegarde les réécrit, chapitre 39.2).

8.5 Étape 5 : systemd

Après le noyau, le premier programme lancé est systemd. Il lit /etc/fstab (quels disques sont montés), démarre les services dans le bon ordre et atteint une cible (target). Pour le bureau, c’est graphical.target.

systemctl get-default                    # welches Ziel gilt
systemd-analyze                          # wie lange der Start dauerte
systemd-analyze blame | head -20         # welche Dienste am längsten brauchten
systemctl --failed                       # welche Dienste nicht starten konnten
journalctl -b                            # alle Meldungen seit dem letzten Start
journalctl -b -p err                     # nur Fehler seit dem Start

8.6 Étape 6 : connexion et session

Le gestionnaire de connexion (sur Raspberry Pi OS avec bureau, le plus souvent LightDM) affiche la connexion ou, avec la connexion automatique, connecte directement l’utilisateur. Il démarre ensuite la session : sur Raspberry Pi OS (Debian 13, « Trixie »), c’est une session Wayland avec le gestionnaire de fenêtres labwc.

echo $XDG_SESSION_TYPE                   # wayland oder x11
loginctl                                 # laufende Sitzungen
sudo nano /etc/lightdm/lightdm.conf      # Anmeldemanager-Einstellungen

8.7 Étape 7 : labwc et le bureau

labwc est le compositeur : le programme qui dessine toutes les fenêtres et fixe le mode d’écran. Au démarrage, il lit ses fichiers selon cet ordre de responsabilité :

Fichier Effet
~/.config/labwc/autostart Programmes lancés au démarrage de la session (p. ex. kanshi &)
~/.config/labwc/rc.xml Comportement du gestionnaire de fenêtres
~/.config/labwc/environment Variables d’environnement pour la session
/etc/xdg/labwc/… Valeurs par défaut du système (les fichiers de l’utilisateur ont la priorité)
~/.config/autostart/*.desktop Démarrage automatique au format standard (entrées de bureau)

Le compositeur interroge le moniteur sur ses capacités (la liste s’appelle EDID) et choisit son mode préféré. Pour un moniteur 4K, c’est 3840×2160 avec une échelle de 1.

8.8 La réponse à « Pourquoi ma résolution est-elle de nouveau perdue après le redémarrage ? »

C’est la raison pour laquelle le sujet de l’écran est devenu si long au chapitre 10. Les étapes s’écrasent les unes les autres :

Où régler la résolution Étape Effet
config.txt (hdmi_group, hdmi_mode) 3 agit sur le firmware et la console ; le bureau se configure ensuite lui-même
cmdline.txt (video=HDMI-A-1:1920x1080@60D) 4 le noyau reprend la valeur (cat /proc/cmdline l’affiche), mais le compositeur à l’étape 7 règle ensuite l’écran à nouveau
wlr-randr dans le terminal 7 agit immédiatement, mais ne vaut que pour cette session (ne figure que dans la mémoire du compositeur)
~/.config/labwc/autostart avec wlr-randr 7 s’exécute à chaque démarrage de session ; sans effet si le moniteur est éteint puis rallumé plus tard
Kanshi (profil) 7 réagit à l’événement « moniteur détecté » et applique le profil
Script de surveillance 7 vérifie toutes les quelques secondes et corrige

La règle qui en découle : le réglage doit se trouver à l’étape qui décide en dernier. Pour le bureau, c’est le compositeur. Tout ce qui se passe avant est écrasé plus tard.

Deux raisons supplémentaires de « disparition » :

  1. Redémarrage du compositeur : un programme qui règle quelque chose avec wlr-randr ne change que l’état en cours. Si la session redémarre, le mode préféré s’applique de nouveau.
  2. Hotplug : si le moniteur est éteint puis rallumé, il se signale de nouveau et le compositeur réinitialise le mode et l’échelle. Une ligne de démarrage automatique ne s’exécute qu’une seule fois à la connexion. C’est pourquoi il faut Kanshi ou un script de surveillance.

8.9 Une liste de contrôle : « Où le démarrage se bloque-t-il ? »

Observation Étape Commande ou indice
Rien à l’écran, la LED verte (ACT) reste éteinte 1–2 Alimentation, carte SD, ordre de démarrage ; Pi 5 : 5 V / 5 A
L’écran reste noir, la LED verte clignote selon un motif 2–3 Le motif de clignotement est un code d’erreur du chargeur d’amorçage (aucun support amorçable, fichier manquant) ; les codes figurent dans la documentation Raspberry Pi. Vérifier la partition de démarrage et le support
Des messages texte défilent puis s’arrêtent 4–5 dmesg, journalctl -b -p err ; lire sur un ordinateur avec la carte
« Waiting for root device » ou rootwait bloque 4 Le PARTUUID dans cmdline.txt ne correspond pas au disque
L’écran de connexion revient sans cesse 6 Droits du dossier personnel, ~/.xsession-errors, journalctl -b
Le bureau apparaît, mais mauvaise résolution 7 wlr-randr, profil Kanshi, démarrage automatique
Un programme du démarrage automatique ne se lance pas 7–8 Lancer le programme dans le terminal, lire le message d’erreur ; placer un sleep avant l’appel

Une deuxième méthode : si le Pi ne démarre pas du tout, brancher la carte SD ou le disque sur un autre ordinateur. La partition de démarrage (FAT) y est visible ; cmdline.txt et config.txt peuvent être corrigés sans que le Pi ait besoin de tourner.

8.10 Phrases à retenir

  • Chaque étape ne lit que ses fichiers ; une modification ne prend effet que quand cette étape tourne de nouveau (le plus souvent : redémarrage).
  • Ce qui est réglé dans une étape ultérieure écrase l’étape précédente.
  • Les réglages que le bureau doit appliquer lui-même relèvent du démarrage automatique du bureau ou de Kanshi.
  • Avant toute modification de cmdline.txt, config.txt, fstab, faire une copie.
