Die Bildschirm-Skalierung ist eines der längsten Themen beim Pi. Hier das Wissen in Ordnung, mit den typischen Fehlversuchen, weil man daraus am meisten lernt.

10.1 Das Problem

Ein 4K-Bildschirm (3840 × 2160 Pixel) zeigt auf dem Pi alles sehr klein: Schrift, Menüs, Symbole. Ich wollte die Auflösung voll behalten (scharfes Bild) und trotzdem alles größer sehen.

10.2 Zwei Grafiksysteme: Wayland und X11

echo $XDG_SESSION_TYPE

Ausgabe wayland oder x11. Mein Raspberry Pi OS (Debian 13, „Trixie") verwendet Wayland mit dem Fenstermanager labwc.

Wayland (neu, bei mir) X11 (älter)
Bildschirm einstellen wlr-randr xrandr
Autostart-Datei ~/.config/labwc/autostart andere

Ich habe X11 ausprobiert. Das Problem wurde dadurch nicht gelöst, deshalb bin ich zu Wayland zurückgegangen.

10.3 Der wichtigste Befehl: wlr-randr

wlr-randr

Er zeigt den Ausgang (zum Beispiel HDMI-A-1 oder HDMI-A-2), die aktuelle Auflösung, die möglichen Auflösungen, Scale (Skalierung) und Ausrichtung. Der Name des Ausgangs ist nicht überall gleich. Immer zuerst wlr-randr ausführen und den Namen ablesen.

wlr-randr --output HDMI-A-2 --mode 1920x1080                  # Full HD
wlr-randr --output HDMI-A-2 --mode 3840x2160                  # 4K
wlr-randr --output HDMI-A-2 --mode 3840x2160 --scale 2       # 4K, alles doppelt so groß
wlr-randr --output HDMI-A-2 --mode 3840x2160 --scale 3       # 4K, dreifach
wlr-randr --output HDMI-A-2 --scale 1                         # zurück
wlr-randr --output HDMI-A-2 --transform 180                   # Bild um 180 Grad drehen
wlr-randr --output HDMI-A-2 --transform normal                # zurück

Bedeutung: Scale 1 = normal, Scale 2 = alles doppelt so groß, Scale 3 = dreifach. Die Auflösung bleibt 4K, nur die Oberfläche wird größer. Bei meinem tragbaren 4K-Monitor war Scale 3 angenehmer als Scale 2.

Für X11 gilt das Gegenstück:

xrandr
xrandr --output HDMI-1 --mode 1920x1080 --rate 60

10.4 Problem 1: Nach dem Neustart ist alles wieder klein

Ein wlr-randr-Befehl im Terminal gilt nur für die aktuelle Sitzung. Beim Neustart wählt Wayland wieder die bevorzugte Auflösung des Monitors. Lösung: ein Autostart-Eintrag.

nano ~/.config/autostart/display.desktop
[Desktop Entry]
Type=Application
Name=Display Setup
Exec=sh -c "sleep 3 && wlr-randr --output HDMI-A-2 --mode 3840x2160 --scale 3"

Das sleep 3 wartet, bis der Desktop fertig gestartet ist. Danach sudo reboot.

10.5 Warum `cmdline.txt` nicht geholfen hat

Auch diese Methode habe ich ausprobiert:

sudo nano /boot/firmware/cmdline.txt

mit dem Parameter video=HDMI-A-1:1920x1080@60D. Alles muss in einer einzigen Zeile stehen. Mit cat /proc/cmdline habe ich geprüft, dass der Parameter vorhanden war. Trotzdem startete Wayland wieder mit 4K, denn der Kernel hat den Parameter übernommen, aber der Desktop hat die Anzeige danach neu eingestellt. Lektion: Eine Einstellung kann in einer Schicht des Systems stehen und in der nächsten überschrieben werden. Deshalb war die Lösung mit wlr-randr im Autostart zuverlässiger.

10.6 Problem 2: Monitor aus und wieder an

Wenn nur der Monitor aus- und eingeschaltet wird, erkennt Wayland ihn neu und setzt die Skalierung auf 1 zurück. Die Autostart-Datei läuft nur beim Login, nicht erneut. Das nennt man ein HDMI-Hotplug-Problem. Es gibt zwei Lösungswege.

Lösung A: Kanshi

Kanshi reagiert, wenn ein Monitor verbunden oder getrennt wird, und wendet ein gespeichertes Profil an.

sudo apt install kanshi
mkdir -p ~/.config/kanshi
nano ~/.config/kanshi/config

Inhalt (so hat es bei mir funktioniert, in der älteren Schreibweise ohne geschweifte Klammern um die Optionen):

profile {
    output HDMI-A-1 mode 3840x2160 scale 3
}

Danach in ~/.config/labwc/autostart die Zeile kanshi & eintragen und neu anmelden.

So habe ich den Fehler gefunden (die Fehlersuche ist die eigentliche Lehre):

  1. ps aux | grep kanshi zeigte nur die grep-Zeile → Kanshi läuft nicht.
  2. Beim manuellen Start kam: unexpected '{' in output – failed to parse config file. Die installierte Version verstand die Schreibweise output HDMI-A-1 { ... } nicht.
  3. Config auf die ältere Schreibweise geändert → Kanshi startete → wlr-randr zeigte Scale: 3.000000 statt 1.000000.
  4. Die Debug-Option kanshi -v gab es in dieser Version nicht (invalid option -- 'v'). Das ist keine Fehlfunktion, nur eine ältere Version.

Lösung B: Watchdog (die „brutale, aber sehr zuverlässige" Lösung)

Ein kleines Script prüft alle paar Sekunden, ob die Skalierung noch stimmt, und korrigiert sie sofort.

nano ~/display_watchdog.sh
#!/bin/bash

while true
do
    SCALE=$(wlr-randr | grep "Scale:" | head -n1 | awk '{print $2}')

    if [ "$SCALE" != "3.000000" ]; then
        echo "Scale falsch → korrigiere"
        wlr-randr --output HDMI-A-1 --scale 3
    fi

    sleep 5
done

Zeile für Zeile:

  • while true; do ... done – Endlosschleife
  • SCALE=$(...) – speichert die Ausgabe des Befehls in der Variablen SCALE
  • if [ "$SCALE" != "3.000000" ] – „wenn die Skalierung nicht 3 ist"
  • wlr-randr --output ... --scale 3 – korrigiert
  • sleep 5 – 5 Sekunden warten (bei sleep 2 reagiert er schneller)

Dann ausführbar machen (chmod +x ~/display_watchdog.sh), mit ~/display_watchdog.sh testen, danach Autostart-Datei anlegen (siehe Abschnitt 5.4). Ein solches Script belastet einen Pi 5 praktisch nicht.

Kanshi oder Watchdog?

Kanshi Watchdog
Prinzip wartet auf das Ereignis „Monitor erkannt" prüft ständig, ob alles stimmt
Wenn der Monitor kein Ereignis meldet wirkt nicht wirkt trotzdem
Aufwand Config-Datei + Programm kleines Script

Mein Verdacht war, dass der Samsung-Monitor beim Aus- und Einschalten kein erkennbares Ereignis sendet. In diesem Fall hilft nur der Watchdog.

10.7 Ausblick: Skalierung automatisch nach Auflösung

Das Konzept: Das Script soll nicht nur die Skalierung prüfen, sondern auch die Auflösung lesen und dann den richtigen Wert wählen.

Auflösung Scale
bis 1920×1080 1
2560×1440 und 3440×1440 2
3840×2160 3

So stellt sich jeder angeschlossene Monitor automatisch richtig ein.
