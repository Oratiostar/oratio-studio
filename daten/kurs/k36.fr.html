36.1 La décision de fond

Le projet B commence par une phrase dont j'ai fait une règle :

app_ui.py lance tout. Chaque onglet et chaque appareil a son propre dossier avec son propre fichier .py et peut être supprimé individuellement.

Un nouvel onglet, c'est donc un fichier plus environ trois lignes dans app_ui.py. Un onglet dont je ne veux plus disparaît quand je supprime son dossier. Le programme démarre quand même.

36.3 app_ui.py : charger les onglets sans qu’un dossier manquant gêne

La particularité de app_ui.py est qu'un onglet manquant n'arrête pas le programme :

def _tab_laden(modul, klasse):
    """Eine Tab-Klasse aus ihrem Ordner holen. Ordner gelöscht oder kaputt?
    Dann gibt es den Tab einfach nicht - der Rest startet trotzdem."""
    try:
        return getattr(__import__(modul, fromlist=[klasse]), klasse)
    except Exception as _ex:
        print(f"Tab {klasse} nicht geladen: {_ex}")
        return None

HomeTab    = _tab_laden("Oratio_Menu.oratio_menu", "HomeTab")
TowerTab   = _tab_laden("Tower.tower_tab", "TowerTab")
MenuTab    = _tab_laden("Oratio_Menu.oratio_menu", "MenuTab")
ToolboxTab = _tab_laden("Oratio_Toolbox.toolbox_menu", "ToolboxTab")
TABS = [("Home", HomeTab), ("Oratio Menu", MenuTab),
        ("Tower", TowerTab), ("Oratio Toolbox", ToolboxTab)]

Ce qui se cache ici :

Élément Signification
__import__(modul, fromlist=[klasse]) charge un module dont le nom existe sous forme de texte
getattr(modul, klasse) en tire la classe portant ce nom
try ... except intercepte toute erreur au chargement
return None « cet onglet n'existe pas »
TABS = [...] l'ordre de la liste est l'ordre dans la barre

Ensuite, la fenêtre principale ne crée plus que les onglets existants :

for name, klasse in TABS:
    if klasse is None:
        continue
    tab = klasse(self.width(), self.height())
    self.tab_widget.addTab(tab, name)

Règle pour chaque classe d'onglet : le constructeur reçoit largeur et hauteur, donc def __init__(self, width, height).

Cette idée traverse tout le projet : une pièce cassée ne doit jamais arrêter l'ensemble. La même astuce (try/except au chargement) se trouve dans les widgets (chapitre 37) et dans la Toolbox.

36.4 Démarrage, redémarrage et installation

run_app.sh lance le programme sans sudo. C'est la conséquence du projet A (chapitre 32.5) : la fenêtre n'a pas besoin de droits système, c'est pourquoi tous les fichiers continuent d'appartenir à l'utilisateur normal. Ventilateur, LED et OLED tournent comme services propres en arrière-plan, qui apportent eux-mêmes leurs droits. Le script a une autre particularité : il redémarre de lui-même après un plantage.

FEHLER=0
while true; do
    START=$(date +%s)
    python3 app_ui.py
    CODE=$?
    [ "$CODE" -eq 0 ] && exit 0          # normales Beenden: nichts neu starten
    NOW=$(date +%s)
    if [ $((NOW - START)) -lt 60 ]; then FEHLER=$((FEHLER + 1)); else FEHLER=1; fi
    echo "Absturz (Code $CODE) - Details in Logs/oratio.log"
    [ "$FEHLER" -ge 3 ] && { echo "Zu viele Abstürze - Abbruch."; exit "$CODE"; }
    sleep 2
done

La logique : si le programme se termine avec le code 0, c'était une fermeture normale. Tout autre code est un plantage, un redémarrage suit après deux secondes. S'il plante trois fois en une minute, le script abandonne pour éviter un redémarrage sans fin.

Journal d'erreurs : les plantages et messages d'erreur vont dans Logs/oratio.log. À partir de 1 Mo, le fichier devient oratio.log.1 et un nouveau commence. En cas de problème, c'est le premier fichier à consulter.

install.sh configure un nouveau Pi d'un seul coup :

  1. Installer Raspberry Pi OS avec bureau, utilisateur oratio.
  2. Copier le dossier entier de l'ancien Pi (clé USB) vers /home/oratio/. C'est la seule façon d'emporter applications, widgets, réglages et la clé PS5.
  3. cd ~/Oratio_Control_Center et bash install.sh. Ne pas lancer avec sudo, le script le demande lui-même.
  4. Suivre les questions, redémarrer à la fin.

Le script peut tourner autant de fois qu'on veut. Il vérifie d'abord s'il se trouve dans le dossier du projet et s'il ne tourne pas en root. Ensuite il installe les paquets (apt) et copie les pilotes LED vers /usr/local/lib.

Sans Internet : les bibliothèques de pilotes Freenove (libfreenove_ws2812_lib.so, libfreenove_pwm_lib.so) se trouvent dans le projet sous LED/Treiber/. Les deux ont besoin de la bibliothèque PIO du Pi (libpio.so.0), normalement présente. On n'a besoin d'Internet que pour la première étape apt, la météo, l'appairage PS5 et les tuiles de mise à jour.

Vérifier sudo sans mot de passe (nécessaire pour redémarrer, éteindre et les interrupteurs d'appareils) :

sudo -k
sudo -n true && echo OK || echo "Passwort wird verlangt"

Si « mot de passe demandé » apparaît, exécuter de nouveau bash install.sh.

Sauvegarde quotidienne des réglages : au démarrage, le programme copie une fois par jour tous les réglages de Json/ vers Json/Backup/<date>/. Les sept derniers jours sont conservés, les plus anciens supprimés. Pour récupérer : quitter le programme, copier les fichiers du dossier daté vers Json/.

36.5 glass_ui.py : la boîte à outils en verre

Tout ce qui est utilisé en commun se trouve dans un fichier d'environ 1700 lignes :

Élément Rôle
S(v) convertit une taille avec le facteur d'échelle : le même code a le même aspect en 1080p et en 4K
paint_glass(p, rect, ...) dessine une surface de verre (translucide, bord clair, reflet)
GlassPanel une fenêtre à l'aspect verre (cadre, barre de titre, bouton de fermeture)
GlassButton, GlassToggle, GlassMiniButton boutons, interrupteurs, petits boutons
GlassTabBar, GlassTabWidget la barre d'onglets avec des capsules de verre
ui_font(px, weight) fournit la police de l'interface (Inter)
set_night_mode, set_accent mode nuit et couleur d'accent pour toutes les fenêtres
load_icon_pixmap, scaled_cached charge les icônes limitées à 512 pixels au maximum et mémorise les images mises à l'échelle
daily_backup, setup_logging sauvegarde quotidienne, journal d'erreurs

Ainsi toutes les fenêtres ont le même aspect, et un changement de l'aspect verre touche tout avec une seule ligne. Dans le projet A, en revanche, chaque tuile était stylée individuellement avec une feuille de style.

Les quatre modes : verre ou mat, chacun en normal ou nuit. Une fenêtre ne demande pas elle-même à quoi elle doit ressembler, mais appelle la boîte à outils. C'est pourquoi une nouvelle fenêtre fonctionne immédiatement dans les quatre modes.

36.6 Où est quoi ? (dans le dossier Oratio_Menu)

Le menu était à un moment un fichier de plus de 10 000 lignes. Je l'ai découpé par thèmes sans changer le comportement (le code est caractère pour caractère le même, simplement classé autrement). Le plan est aujourd'hui la carte du projet :

Kern/ – briques de base sans fenêtre

Fichier Contenu
abhaengigkeiten.py éléments facultatifs avec remplacement (barre de fenêtres, réglages de barre par défaut)
konstanten.py nombres fixes : limites de la grille, tailles de symboles, palette de couleurs, types de fenêtres d'applications
stil.py style verre de la fenêtre de contrôle
symbole.py tous les symboles dessinés soi-même (draw_..._icon)
modell.py MenuItem et le calcul de la grille (pages, places libres)
umzug.py déménagement unique des anciens dossiers et fichiers JSON au démarrage
programme.py programmes installés, modes de lancement, installation
system.py lancer des commandes, activer WLAN/Bluetooth, luminosité, son

Bausteine/ – composants visibles : kacheln.py (tuile d'application, grille, points de page, image glissée), menueleiste.py (barre de verre en haut), dock.py, kontrollzentrum.py (fenêtre de contrôle).

Fenster/ – fenêtres de verre : einstellungen.py, verbindungen.py (WLAN, Bluetooth, microphone, énergie), apps.py (ajouter/modifier une application, médiathèque), galerie.py (galerie de widgets), zentrale.py (la liste de tous les réglages).

Ansicht/ – la vue principale MenuView en plusieurs parties (toutes ensemble forment une classe) :

Fichier Contenu
ansicht.py Structure, taille, dessin, événements
speicher.py Chargement, enregistrement, profils, sauvegarde
leiste.py Barre de menu et fenêtre de menu
fenster.py Overlay en haut à droite, fenêtre de pages, clic sur les symboles
design.py Style, mode nuit, effets, police, arrière-plan, aspect du dock
laufende.py Barre des fenêtres en cours
raster.py Pages, tuiles, mode édition, changement de taille
dock_ops.py Applications vers le dock et hors du dock
ziehen.py Glisser des applications dans la grille
tastatur.py Commande au clavier et au joystick
starten.py Lancer, créer, supprimer des applications et widgets

Technique de la répartition : MenuView hérite de plusieurs classes « Mixin », une par fichier (class MenuView(ZiehenMixin, RasterMixin, ...)). Chaque fichier ne contient qu'une partie des méthodes, ensemble elles forment une classe.

Où va une nouvelle fonction ? Dans un fichier propre (comme mitteilungen.py, suche.py) ou comme fenêtre propre dans Fenster/ – pas de nouveau dans un fichier géant.

L'inconvénient que je note honnêtement : une nouvelle idée touche souvent plusieurs parties qui doivent s'accorder (vue, fenêtre, recherche, liste des réglages). Avec un fichier unique, on peut tout chercher et remplacer d'un coup ; avec beaucoup de fichiers, il faut savoir lesquels vont ensemble. Les mises à jour du guide indiquent donc toujours quels fichiers changent.

Fichier Contenu

oratio_wetter.json Lieu pour la météo
oratio_stimme.json Commande vocale
oratio_sperre.json Écran de verrouillage (le code n'est stocké que sous forme de somme de contrôle)
oratio_fokus.json Profils de concentration
oratio_nutzung.json Statistiques d'utilisation
Json/Profile/<Name>/ Profils de réglages enregistrés

Une entrée de oratio_apps.json ressemble à ceci :

{"name": "Icon Werkstatt",
 "file": "/home/oratio/Oratio_Control_Center/Oratio_Menu/Apps/Icon_Werkstatt/icon_werkstatt.py",
 "icon": "Oratio_Menu/Apps/Icon_Werkstatt/icon.png",
 "color": "#000000", "terminal": false, "embed": true,

Clé Signification

icon Image de la tuile
color Couleur de la tuile

Un widget a, au lieu de file, la clé "widget": "network" ainsi que w et h pour la taille en cases.
