32.1 Ausgangspunkt: das Freenove-Programm

Der Freenove-Tower (Kapitel 11) bringt eine fertige Python-Oberfläche mit. Sie hat vier Tabs:

Monitor | LED | Fan | OLED

Die Datei app_ui.py baut das Hauptfenster. Jeder Tab ist eine eigene Klasse, die zu einer eigenen Datei gehört (LED, Lüfter, OLED). Gestartet wird die Oberfläche mit python3 app_ui.py oder über ein kleines Startskript run_app.sh. Auf diesem Aufbau beruht alles Weitere. Dass Qt (die Oberflächen-Bibliothek) ein Tab-Widget (QTabWidget) mitbringt, in das man beliebig viele Tabs hängt, ist die Grundlage der nächsten Schritte.

Merke: Wer ein fremdes Programm erweitert, erweitert zuerst eine Kopie. Ich habe den Ordner mit allen Python-Dateien kopiert und nur in der Kopie gearbeitet. So blieb das Original zum Vergleichen übrig.

32.2 Ziel: ein Tab „Scripts“

Ich wollte rechts neben OLED einen fünften Tab:

Monitor | LED | Fan | OLED | Scripts

Beim Anklicken sollten vier Rechtecke (Schaltflächen) erscheinen, jedes mit dem Namen eines Skripts. Ein Klick auf ein Rechteck startet das Skript. Die ersten Skripte waren Programme, die ich schon hatte: ein Datei-Prüfer (Hash-Checker, siehe Kapitel 45), ein Backup, ein OLED-Test und ein Update-Skript.

32.3 Die neue Datei

Der Tab bekommt eine eigene Datei, damit app_ui.py nicht noch länger wird: app_ui_scripts.py. Darin steht eine Klasse mit einem Raster (QGridLayout) und vier Schaltflächen:

from PyQt5.QtWidgets import QWidget, QPushButton, QGridLayout
import subprocess

class ScriptsTab(QWidget):
    def __init__(self):
        super().__init__()
        layout = QGridLayout()
        self.btn1 = QPushButton("Backup")
        self.btn2 = QPushButton("Update")
        self.btn3 = QPushButton("OLED Test")
        self.btn4 = QPushButton("Hash Checker")
        layout.addWidget(self.btn1, 0, 0)
        layout.addWidget(self.btn2, 0, 1)
        layout.addWidget(self.btn3, 1, 0)
        layout.addWidget(self.btn4, 1, 1)
        self.setLayout(layout)

        self.btn1.clicked.connect(lambda: self.run_script("backup.py"))
        self.btn4.clicked.connect(lambda: self.run_bash("hashchecker.sh"))

    def run_script(self, filename):
        try:
            subprocess.Popen(["python3", filename])
        except Exception as e:
            print(e)

    def run_bash(self, filename):
        try:
            subprocess.Popen(["lxterminal", "-e", f"bash {filename}"])
        except Exception as e:
            print(e)

Was die Teile tun:

Teil Bedeutung
QGridLayout ordnet Elemente in Zeile und Spalte an: addWidget(element, zeile, spalte)
QPushButton("Text") eine Schaltfläche mit Beschriftung
.clicked.connect(...) verbindet den Klick mit einer Funktion
lambda: ... eine kleine namenlose Funktion; nötig, damit der Dateiname beim Klick mitgegeben wird
subprocess.Popen([...]) startet ein anderes Programm, ohne dass die Oberfläche wartet
lxterminal -e ... öffnet ein Terminal-Fenster und führt dort einen Befehl aus

32.4 Den Tab in app_ui.py einhängen

In app_ui.py sind nur drei Stellen nötig:

  1. oben from app_ui_scripts import ScriptsTab,
  2. dort, wo die Tabs angelegt werden, self.tab_widget.addTab(ScriptsTab(), "Scripts"),
  3. speichern und neu starten.

Das ist das Prinzip für jeden weiteren Tab: eigene Datei mit einer QWidget-Klasse, ein import, ein addTab.

32.5 Der Hash-Checker lief nicht aus dem Control Center

Das Skript hashchecker.sh ist ein Bash-Skript (Shell), kein Python-Skript. Mit python3 hashchecker.sh ließ es sich nicht starten. Deshalb die zweite Funktion run_bash, die es in einem Terminal-Fenster mit bash ausführt. Das Skript selbst habe ich vorher im Terminal geprüft, weil das die schnellste Fehlerquelle ausschließt:

cd ~/Dokumente/Code
bash hashchecker.sh

Läuft es dort nicht, liegt der Fehler im Skript. Läuft es dort, aber nicht aus dem Control Center, liegt er in der Oberfläche.

Der Fehler mit sudo

Genau dieser Fall trat auf: Aus dem Terminal gestartet (python3 app_ui.py) lief alles, über ./run_app.sh startete der Hash-Checker nicht. Der Vergleich der beiden Wege ergab: In run_app.sh stand sudo python app_ui.py. Damit läuft das ganze Programm als Benutzer root, und root hat einen anderen Home-Ordner, andere Pfade und eine andere Umgebung als der Benutzer oratio. Skripte, die relative Pfade oder die Anzeige des normalen Benutzers brauchen, scheitern dann.

Die Lösung: das Programm als normaler Benutzer starten und nur dort sudo verwenden, wo ein einzelner Befehl es wirklich braucht.

Merke: Läuft etwas im Terminal, aber nicht per Startskript oder Symbol, dann unterscheidet sich die Umgebung: Benutzer, aktueller Ordner, Umgebungsvariablen. Zuerst vergleichen, nicht raten. Ein einfacher Test: in die Funktion print(os.getlogin()) und print(os.getcwd()) einbauen und beide Wege ausprobieren.

32.6 Skript starten oder in eigenem Fenster?

Zuerst startete das Skript im selben Fenster wie die Oberfläche und überdeckte sie. Ein eigenes Fenster (Terminal oder QProcess) ist die bessere Lösung. Merksatz: Die Oberfläche startet Programme, sie wird nicht selbst zum Programm.

32.7 Wenn der Tab sich nicht einhängen lässt: Einrückung

In diesem Abschnitt der Arbeit tauchte der häufigste Anfängerfehler mit Python auf: Einrückung. Python erkennt Blöcke an den Leerzeichen am Zeilenanfang. Mischt man Tabulatoren und Leerzeichen, sieht der Code im Editor richtig aus und bricht trotzdem ab:

TabError: inconsistent use of tabs and spaces in indentation
IndentationError: unexpected indent

Ursache war mein Editor (Geany): Er fügte teilweise Tabulatoren ein, ich selbst tippte Leerzeichen. Merkregeln:

  • Vier Leerzeichen pro Ebene, nie Tabulatoren.
  • Im Editor einstellen, dass die Tab-Taste Leerzeichen einfügt.
  • Prüfen ohne Start: python3 -m py_compile datei.py meldet die Zeile.
  • Gemischte Datei bereinigen: expand -t 4 datei.py > datei_neu.py.

Was beim Einfügen von Code aus einer Anleitung besonders oft schiefgeht: Der neue Block muss genau auf derselben Ebene beginnen wie die Zeilen daneben. Tipp: erst die Zeile davor markieren und die Einrückung ansehen, dann einfügen.

32.8 Die Methode, nach der ich arbeitete

Aus diesem Kapitel nehme ich mit, wie ich jeden weiteren Schritt anging:

  1. Eine Sache pro Schritt ändern, danach starten und testen.
  2. Im Terminal starten (python3 app_ui.py), nicht über ein Symbol, damit Fehlermeldungen sichtbar sind.
  3. Bei jeder Änderung wissen, in welcher Datei und an welcher Stelle sie steht.
  4. Ein Fehler wird erst eingegrenzt (Skript allein, Oberfläche allein), dann behoben.
  5. Eine laufende Version sichern, bevor ich weiterbaue.
