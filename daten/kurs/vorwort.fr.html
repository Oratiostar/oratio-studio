Ce livre est à la fois un cours, un ouvrage de référence et un livre d'atelier. Il commence par les premières commandes de terminal et mène, en passant par le Raspberry Pi, les microcontrôleurs, les écrans, les matrices de LED, les systèmes d'exploitation et l'IA locale, jusqu'à une grande réalisation personnelle, l'Oratio Control Center. À la fin figurent un dépannage détaillé, un lexique des erreurs et une grande partie consacrée à l'électronique.

Je suis électronicien de métier et j'ai appris Linux, les microcontrôleurs et la programmation en autodidacte, par passion. Le livre consigne ce que j'ai appris en chemin : non seulement ce qui fonctionne, mais aussi ce qui n'a pas fonctionné et pourquoi. Ce sont justement les échecs qui ont apporté le plus de savoir.

Comment les textes sont écrits

  • Les récits d'expérience sont écrits à la première personne (« J'ai essayé X, cela a échoué parce que … »). Pour les problèmes, on trouve d'abord l'essai qui n'a pas fonctionné, puis la solution, et toujours la raison pour laquelle elle fonctionne.
  • Les instructions sont rédigées de façon neutre ou à l'impératif (« ouvrir le fichier, chercher la ligne, enregistrer »), pour qu'on puisse les refaire comme une recette.
  • Chaque idée figure une fois, à l'endroit où elle devient importante pour la première fois. Les leçons valables dans plusieurs projets sont rassemblées dans la partie transversale (partie 15).

Trois chemins à travers le livre

  1. De l'avant vers l'arrière. Qui commence de zéro lit les parties 1 et 2, puis choisit un projet.
  2. Par projet. Chaque partie de projet est autonome et indique au début ce qui est supposé connu. Le Control Center (partie 14) est décrit de façon à pouvoir être reconstruit pas à pas.
  3. En cas d'erreur. D'abord le chapitre 47 (méthode), puis le chapitre correspondant au symptôme dans la partie 16. Ensuite le lexique des erreurs (partie 17) ou l'index des erreurs (annexe D). Le but est que de nouveaux problèmes puissent être cernés sans aide extérieure.

Ce qui figure dans les encadrés

  • Les commandes figurent dans des cadres gris et se tapent exactement ainsi dans le terminal.
  • Une commande précédée de sudo s'exécute avec les droits d'administrateur. C'est puissant ; de telles commandes sont vérifiées deux fois auparavant.
  • Les textes entre chevrons comme <NAME> sont des espaces réservés qu'il faut remplacer.
  • Les tableaux Symptôme → Commande → Interprétation → Suite (partie 16) sont faits pour la consultation.

Ce qui ne figure pas dans ce livre

  • Pas le code source complet de tous les projets. Le livre contient du code d'exemple et les extraits décisifs, pour que la structure soit compréhensible et reconstructible ; le logiciel complet se trouve dans les dossiers des projets.
  • Tout n'est pas testé avec la même rigueur. Quand une fonction n'a été vérifiée qu'en essai à blanc ou dans un environnement de test, c'est indiqué expressément (par exemple pour le clone de sauvegarde, le point d'accès, la caméra, la commande vocale avec un vrai microphone).
  • Les valeurs d'électronique n'ont pas été vérifiées composant par composant par rapport à la fiche technique (partie 19).

Toutes les commandes sont écrites pour Raspberry Pi OS (Debian 13, « Trixie ») avec Wayland. Quand quelque chose ne vaut que pour Windows ou seulement pour un appareil précis, c'est indiqué.
